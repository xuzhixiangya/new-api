# 智能路由与调用日志

网关新增两项能力：

- **智能路由**：用户把模型写成 `auto` 时，按请求难度换成便宜、中等或顶尖模型，再按换成后的模型选渠道和计费。
- **调用日志**：把对话原文留给管理员事后查看。使用日志记费用和模型，调用日志记当时说了什么、回了什么。

## 智能路由

只对下面几类请求生效：

- `POST /v1/chat/completions`
- `POST /v1/responses`
- 后台体验区的对话

图片生成、向量、语音等接口不会改模型。用户写了具体模型名时，默认也不改，原样转发。

### 打开并配置

路径：**系统设置 → 模型 → 智能路由**。

1. 打开「启用智能路由」。
2. 便宜模型、中等模型、顶尖模型三个都要填。少一个，功能就不算配好。
3. 分类模型可以空着。空着就用便宜模型。只有网关自己拿不准时才会问它一次。
4. 分类超时按毫秒填写。实际至少等 2 秒。超时、失败，或分类结果没把握，就用中等模型。
5. 保存。配置写在数据库里，重启仍然有效。

三档都填好，并且该用户的令牌至少允许其中一个模型之后，模型列表里才会出现 `auto`。

### 用户怎么调用

和普通对话一样，把模型名写成 `auto`：

```json
{
  "model": "auto",
  "messages": [
    { "role": "user", "content": "把这段话翻译成英文：今天下午三点开会。" }
  ]
}
```

没配好就发送 `auto`，请求会直接失败，不会悄悄换成别的模型。

### 强制某个用户一直走路由

在 **用户** 里编辑该用户，打开「强制智能路由」。

打开之后，这个用户的对话和 Responses 请求都会重新选模型，即使请求里写了固定模型名。原始模型名仍记在使用日志里。开关打开时，智能路由必须已经配好，否则该用户的对话请求会失败。

### 会落到哪一档

网关先在本地看最后一句和上文。拿得准就直接定档，拿不准再问分类模型。

| 用户在说什么 | 一般落到 |
| --- | --- |
| 翻译、润色、提取、总结、问天气，句子也不长 | 便宜 |
| 普通写脚本、改一改、设计一段文案，本地吃不准 | 中等 |
| 架构、分布式、事务、从零设计、一致性这类难题 | 顶尖 |
| 翻译里夹了「分布式」这类难题 | 顶尖，难题优先 |
| 带图、多个文件、三个及以上工具，或要求按 JSON 结构输出 | 至少中等 |
| 上文特别长 | 很长至少中等，特别长直接顶尖 |

多轮对话里，短跟进会接着上一轮的难度。例如架构聊完再说「为什么」或「好的继续」，还会走顶尖。下面这些不会继承上一轮：

- 「谢谢」「好的」「你好」
- 换成新任务，比如架构聊完再说「帮我写个请假理由」
- 换题去问天气

「总结一下」「提取要点」如果前面已经有一大段内容，至少走中等，不会掉回便宜。

令牌如果限制了可用模型：选中的那一档不在允许列表里时，会往更高一档找（便宜不行找中等，中等不行找顶尖）。更高的也不允许，请求会被拒绝。不会为了凑合降到更便宜的模型。

分类这一步由网关拿渠道密钥直接问上游，不会给用户再记一条使用日志。用户只按最终选中的模型计费。分类调用会消耗对应渠道的上游额度。分类失败不影响主请求，主请求会落到中等模型。

### 在使用日志里核对

打开 **使用日志**。时间默认是今天。走了智能路由的记录，模型列会叠两行：上面是用户原来写的模型（通常是 `auto`），下面是实际使用的模型。

点开详情，有一块「智能路由」：

| 字段 | 含义 |
| --- | --- |
| 档位 | `cheap` 便宜，`mid` 中等，`strong` 顶尖 |
| 阶段 | `local` 本地规则定的，`classifier` 分类模型定的，`fallback` 分类没成功、回落到中等 |
| 续写 | 是不是接着上一轮的难度 |
| 原因、分数 | 排查用。分数越高越难 |

没有这块，说明这次没走智能路由。固定模型名、而且这个用户没被强制时，就是这种情况。

## 调用日志

调用日志记录对话原文，供管理员排查「为什么这么答、为什么走了这个模型」。只有管理员能看。普通用户看不到这个页面，也调不了对应接口。

### 打开记录

路径：**系统设置 → 运维 → 日志维护**。打开「记录调用日志」并保存。

关掉之后，新请求不再记对话。已经记下的还在，直到清理。记录是异步写的，请求返回之后才会出现。

会记录这些协议的文本对话：Chat Completions、Responses、Claude、Gemini。图片和文件只记「这里有图 / 有文件」，不保存文件本身。助手回复过长会被截断，详情里会标「已截断」。流式中途断开，会标成不完整或客户端断开。

### 在哪里看

左侧 **管理 → 调用日志**。

默认只看今天。可以按这些条件筛选：

- 协议、状态（成功、失败、不完整、客户端断开、超时）
- 用户 ID、用户名（至少两个字时按前缀匹配）
- 令牌、模型、请求 ID
- 时间范围

点开一条，可以看到用户、令牌、模型、协议、耗时，以及按角色排好的对话。这里的模型名是实际使用的模型，不是用户写的 `auto`。可以在对话里搜索，也可以复制单条消息。

### 从使用日志跳过来

管理员在 **使用日志** 或 **任务日志** 里打开某条详情。有请求 ID 时会出现「调用日志」。

- 有记录：点「查看调用日志」，打开同一条请求的对话。
- 没有记录：显示没有捕获到。常见原因是当时没开记录、协议不在记录范围内，或者日志已经被清掉。

两边用的是同一个请求 ID。

### 清理

还是在 **系统设置 → 运维 → 日志维护** 的「清理历史日志」。选定时间点后清理，该时间之前的使用日志和调用日志会一起删除，无法恢复。调用日志里有用户原文，不需要长期留存时定期清理。

## 建议的核对步骤

1. 配好三档模型，打开智能路由，再打开调用日志记录。
2. 用测试令牌发一条模型为 `auto` 的简单翻译，再发一条架构设计。
3. 到使用日志看：翻译应落到便宜模型，架构应落到顶尖模型。详情里能看到档位和原因。
4. 在同一条详情里点「查看调用日志」，核对用户原话和模型回复是否对应该次路由。
